# DC-57 — a line that arrives with a switch command is answered by the session you are leaving

- **id:** DC-57
- **class:** input handoff across a session switch
- **severity:** **P2.** The prompt is durable where the human did not aim it:
  a batch that carries a switch and a prompt runs the prompt in the OLD
  session's context (and pays for it), then switches. Invisible unless the
  logs are read.
- **agent:** the switch machinery as it stood in 0.40.0; found while fixing
  DC-55.
- **found by:** the agent, during the DC-55 investigation (a hermetic probe).
- **status:** **FIXED** in this round, by the owner's ruling of 2026-09-21
  (option ①: queue the line for the new session).

## The reproduction (hermetic, scripted faux provider, no model call)

```
printf '/resume alpha\ntell me about widgets\n' | kiso chat fresh
```

Before the fix: `fresh.jsonl`'s last `user_input` was `tell me about widgets`
and the switch to `alpha` happened afterwards. The same batch shape with two
switch commands opened only the second target — the same handoff seen from the
other side.

## Why "the same batch" is not exotic

A switch is not applied when it is requested: `/resume <id>` sets a pending
target and `chat()` returns; the loop opens the new session afterwards — and
the request itself is made from INSIDE a dispatch-chain segment. A terminal
paste, a pipe or a scripted driver delivers several lines in one read, and the
chain is FIFO: a line that arrived *before* the switch was requested still runs
its segment *after* it. One line at a time by hand never shows this; a paste
does.

## The fix

The departing entry answers nothing: the guard sits at the input edge AND at
the dispatch edge (the second is what actually closes the race above), and the
line goes into `queuedSwitchLines` (state), which the next `chat()` drains into
the queue it already replays for pre-ready lines. The switch and reload arms of
`ChatEnd` carry the queued lines, so nothing is dropped either.
