# 0.42.2 — dogfood checklist (for the owner's manual pass)

The release rule: after the publish, the agent runs one real-model session
on a real task, and the owner runs an independent pass. Both go into the
record before 0.42.2 is APPROVED.

```
npm install -g @vincemakes/kiso-code@0.42.2
kiso --version        # 0.42.2
```

## A. Nothing changed for kiso-code on the first-party route — and that is the check

0.42.2 reads a gateway's reported cache WRITE into the usage event and
subtracts it from the fresh count. The first-party DeepSeek route reports
no cache write, so on it the arithmetic reduces to 0.42.1's. A normal
session behaves as 0.42.1 did; `/status` ends with `version 0.42.2`; the
`fresh` / `cache` figures on the status line read as before.

## B. If you have a gateway profile that reports the write

A session through it: the trace's request records carry `cacheWrite`
(non-null) and `freshInput` = prompt − cached − written. That is the live
half of this provider round; the first product's cold-turn reconciliation
is the other record of it.

## C. What would be a finding

- A session that behaves differently from 0.42.1 on the same task.
- A `fresh` figure that changed on the first-party route (it must not).
- A usage record with `cacheWrite: 0` where the provider reported nothing.
