# 0.42.0 — dogfood checklist (for the owner's manual pass)

The release rule: after the publish, the agent runs one real-model session
on a real task, and the owner runs an independent pass. Both go into the
record before 0.42.0 is APPROVED.

```
npm install -g @vincemakes/kiso-code@0.42.0
kiso --version        # 0.42.0
```

## A. kiso-code — a normal session is the check

0.42.0 changes the kernel loop (the END_TURN check at the head of every
turn) and the runtime's prompt composition (the appends composed once per
attempt by the outermost adapter layer). kiso-code uses neither the
`END_TURN` tag nor a function append, and its request bytes are pinned
unchanged by the byte fixture — so a normal session on a real task must
behave as 0.41.2 did: the same tool calls, the same prompt prefix at the
cache-hit price, `/status` ending with `version 0.42.0`.

Suggested: a multi-step edit task with a test run (the ledger fixture or
any repo), then `/status`. Look at `cache` in the status line — a prompt
that changed between requests would show as fresh input, not cache.

## B. The task extension's append still composes

`/status` or the trace's rent ledger shows `system:ext:task`. The task
extension's append is a string; nothing changes for it.

## C. What would be a finding

- A session that behaves differently from 0.41.2 on the same task.
- A drop in the cache ratio between requests within one turn (the
  per-attempt composition changed the prefix).
- A run that ends after a tool result without the model's final text
  (an END_TURN decision where no tool tagged one).
